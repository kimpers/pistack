### Autopilot-full

Read [the Pi integration contract](../../../../pi/references/integration.md) first. Paths in prose are relative to the poteto-mode skill directory unless explicitly linked.

**You own the verdicts, never the PRs. One owner carries each PR from build to merge. Nothing merges until independent verification proves the code that lands.** For a queue of independent PRs with explicit landing authority. Orchestrate instead runs a standing program whose workers never merge.

Read [runtime](../../../../pi/references/runtime.md) and [delegation](../../../../pi/references/delegation.md). A PR owner is a parent-managed sequence of bounded local worker phases, not a nested orchestrator. Packaged children return patches and evidence. The parent schedules reviews and authorized forge operations. Keep one writer per cwd, apply captured managed patches before publication, and never assume a managed worktree persists. Helper-dependent steps require current readiness and relevant qualification. Publication and landing are parent-owned and require explicit authorization. An assigned owner lifecycle is not a child permission grant.

Assess task difficulty through the approved model policy before dispatch. Keep exact approved selectors, inherited effort, saved panel sizes, and configured concurrency. Effort, speed, or family changes need explicit approval.

A verdict covers one patch, and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. Shipping's patch-id rule can carry a lane's result, but every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the named queue. Operator-owned items and PRs outside it stop at merge-ready. A request to state the plan is not a go. Only explicit continuation authority permits a pi-goal objective and optional user-selected budget under the runtime contract. Never replace an unrelated goal.
2. **Assign one owner per PR and preserve its work.** Resolve the forge once. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for PR operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Each parent-managed owner builds, opens its PR per `playbooks/opening-a-pr.md`, proves the real artifact, triages Bugbot skeptically per `references/bugbot-triage.md`, and babysits to green per `playbooks/babysit.md`. Steps 4 and 5 gate any authorized merge.

   Open the PR early within explicit publication authority so CI and bots run alongside the work. Otherwise return the patch and record publication skipped. Code-ready follows the attributed local **deslop** and `/skill:no-comments` passes. Then rebase onto current trunk and report the code-ready head before self-proof. Report every later head, and merge-ready once self-proof, CI, and babysit finish. Fix rounds keep that base unless trunk conflicts or breaks CI. Run the repository's touched-path checks on the committed head before code-ready and later pushes that need a verifier. A hook pass is not proof.

   Start a `decisions.tsv` trail early per **show-me-your-work**, in the approved task-local artifact directory. Preserve a checkpoint at every verified-unit boundary. Commit and push with hooks enabled only under explicit publication authority. Otherwise retain the patch and evidence locally. Expected-red states stay inside their verification unit, never a publishable checkpoint. The parent records each native child ID, state, and expected runtime based on observed comparable runs in task-local `children.tsv`. Native status and captured handoffs remain authoritative. Publish a rewritten owned branch only with explicit permission, an `ls-remote` check, and `--force-with-lease` pinned to the SHA last pushed or explicitly taken over. An unexpected push stops publication for reconciliation, never an updated lease that overwrites it. Never force-push a shared branch.
3. **Run independent owners in parallel off trunk, never stacked.** Each PR lands on its own. Serialize overlapping files and shared checkouts. Dependent work is merge-then-branch, or belongs in Autopilot-stack rather than a private exception here.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head. Start a round at the code-ready head SHA. The parent dispatches independent verifiers per **swarm**, re-runs gates, proves load-bearing behavior through the existing app harness or authorized Pi browser or PTY profile, and audits the diff in at least two focused review lanes with the full brief. Distrust the PR body. Audit merge-ready receipts before the verdict. A verdict without the required live lane is not clean.

   Include a regression lane against trunk. If trunk lacks the feature, record that fact and gate the added behavior and the user's end state instead of inventing a trunk result. A defect already on trunk is recorded against trunk and does not gate this PR unless the PR copies or newly reaches it. Send every proven finding to the owner in one fix-forward, including defects filed as notes. Request a red test across all sites with the same defect, or a repro receipt when no test can expose it. Add the defect to the next brief. Never push a fix behind the owner. Confirm settlement before replacing it. A single verifier checks the new head and affected behavior, reconciles earlier findings, and audits which prior lanes remain valid under Shipping's stricter per-lane reuse rule. Missing required proof stays blocked. Merge needs a clean verdict whose patch matches merge-ready.
5. **Merge only verified code tested on the trunk it lands on.** Green CI alone never authorizes merging. Merge prep begins after the swarm's lanes start, includes a merge-prep rebase onto current trunk, and reports the new head. CI must pass at that exact head. Apply Shipping's stricter per-lane evidence reuse, not patch-id equality alone.

   Immediately before the authorized merge, obtain fresh trunk and check `git merge-tree`. A conflict, overlapping changed code, or changed CI-selection paths requires a rebase and fresh CI. A shared lockfile change can avoid a rebase only if an explicitly authorized frozen install passes on the merge result and packages changed by the PR resolve there as on the head. A failed install means rebase and repair. When trunk changes a caller or dependency of the patch, run the patch's checks on the merge result and require a pass. Unknown impact, CI-selection coverage, or evidence validity means rebase and reverify, not a guessed pass. Otherwise a later trunk move need not restart CI. If trunk would force a third rebase past merge prep, hold for the root to sequence the colliding work.

   The parent performs the authorized merge through the resolved forge and confirms that it actually merged, not merely queued. The settled owner returns, and a fresh owner takes the next item with consolidated scope and evidence. The operator's landing grant plus the clean verdict is the authorization that Babysit alone never has. Operator-owned items wait for the operator's click.
6. **Run the root layer.** Anything that loosens a gate, including a raised budget or an allowlist entry, needs verifier proof and a fresh root countersign. The countersign is approval only within the operator's explicit grant. Record it for a lane to check. It cannot impersonate human, tool, or forge approval. Remove a proposed disabled or soft-failed check rather than weakening the gate to get green. Absorbing a value already landed on trunk is drift, not a new raise.

   Run an audit tick every hour only under explicit continuation authority. Use an owned finite interactive-shell event monitor or audit wait under the runtime contract, alongside native child notifications. It wakes the existing authorized task, not another goal or executor. Re-read this packaged Pi-adapted playbook by resolved local path, not the target project's trunk, and inspect current goal status. Have owners record missing heads or receipts. Such drift is a record gap, not proof of a stall.

   Probe every owned run down to the leaf lanes and collect the trails. Compare native status and actual outputs with expected runtime. Read-only work need not produce side effects. Silence alone never proves a stall, and waiting on the root or operator is not stuck work. Answer pending decisions. A lane error blocks its work. For a diagnosed stall, checkpoint and interrupt or stop the exact owned run. Confirm settlement and preserve its partial diff before a same-protocol replacement; unknown ownership blocks a second writer. Never drop a stalled lane's work. End only when every delegated run is settled, even after the final merge. Run a retro and post-merge bot-comment sweep when merges batch. Use **ketchup** for changes the operator has not heard. Otherwise omit routine status text, never a required blocker or approval response.
7. **Stand down at once on the operator's stop.** Follow Pause safely. Send zero-new-writes guidance to exact owned workers, reconcile interruption and artifacts, stop owned monitors, and request the user's goal pause. A receipt does not prove a worker stopped. Unrelated workers and goals stay untouched.

**Reply:** use **ketchup** for each PR's state and verdict, what merged, countersigns and why, and open operator gates. Link each PR and the trails. Keep exact heads, verifier identities, and queue ownership in the linked evidence.
