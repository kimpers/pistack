### Autopilot-full

Read [the Pi integration contract](../../../../pi/references/integration.md) first. Paths in prose are relative to the poteto-mode skill directory unless explicitly linked.


**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. The job is a queue of independent PRs handed over to drive to merged with full autonomy. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge; here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

Read [runtime](../../../../pi/references/runtime.md) and [delegation](../../../../pi/references/delegation.md). A PR owner is a parent-managed sequence of bounded local worker phases, not a nested orchestrator. Packaged children return patches/evidence; the parent schedules reviews and authorized forge operations. Keep one writer per cwd, apply captured managed patches before publication, and never assume a managed worktree persists. Helper-dependent steps require current readiness and the relevant qualification. Publication and landing are parent-owned and require explicit authorization; an assigned owner lifecycle is not a child permission grant.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go. On that go, use the explicit pi-goal objective and optional user-selected token budget per the runtime contract. Do not replace an unrelated goal. The goal continues across turns until the queue is done.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR create, edit, view, watch, and merge operations; otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One local Pi owner per PR owns build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical Bugbot triage per `references/bugbot-triage.md`, a slop-strip (the attributed local **deslop** skill), `/skill:no-comments` (the **no-comments** skill), a rebase onto current trunk, the babysit loop to green (`playbooks/babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft, only within explicit publication authority; otherwise return the patch and record publication skipped. Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. The parent records each child ID, expected runtime based on observed runs (at least the longest comparable run), and state in a bounded task-local `children.tsv`, retained with the reports. Native status and exact owned IDs remain authoritative, not this receipt. The first rebase precedes the code-ready report and babysit. Keep that merge base in fix rounds; rebase again only at merge prep, on a `git merge-tree` conflict with trunk, or a CI failure caused by trunk. After the slop-strip and `/skill:no-comments`, report the code-ready head SHA and each later patch-changing push. Self-proof, CI and babysit may run alongside independent swarm verification. Report merge-ready with its exact SHA once those checks finish. Before a round-starting push, run the repository's touched-path pre-review checks on the committed head; a hook pass is not proof. Publishing a rewritten owned branch requires explicit permission, an `ls-remote` check and a lease, never a force-push of a shared branch. Step 4 gates any separately authorized merge.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify every round before its merge.** Start a round at the code-ready head SHA and each later patch-changing push. The parent fans out independent verifiers per **swarm** at that SHA. Re-run gates, prove load-bearing behavior live through the existing app harness or authorized Pi browser/PTY profile, and audit the diff in at least two focused review lanes with the full brief. Focuses can include consumer parity, lifetimes/races, and data/config safety. Distrust the PR body. Audit merge-ready receipts before the verdict. Include a **Regression lane against trunk.** Run the same load-bearing scenario on trunk; if the feature is absent, record that and gate added behavior plus the end state rather than inventing a trunk result. A verdict without the required live lane is not clean. Send every proven finding to the owner in one fix-forward, including defects filed as notes. For every behavior finding request a red test across all matching sites, or a repro receipt where no test can expose it. Add it to the next round's brief. The new head needs a fresh swarm/verdict except for specific lane results valid under Shipping's patch-id rule. Merge needs a clean verdict whose patch matches merge-ready.
5. **On a clean verdict the owner merges and takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep starts only after the round's lanes start and ends with a rebase onto current trunk immediately before merge. Report the new head SHA; CI must pass at that head. Apply Shipping's patch-id rule to each retained lane result. If trunk moves again before the merge, the patch-id rule in `playbooks/shipping.md` governs re-verification; a new head requires the patch-id and lane-result checks, not a claim based on a prior green head. The owner squash-merges its own PR through the resolved forge and picks up its next self-contained item from the queue. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value needs verifier proof and the required approval. A root countersign is evidence only within the operator's explicit grant; it cannot impersonate human, tool or forge approval. Record any permitted countersign and have a lane check it. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners roughly every 30 minutes. Use an explicitly owned finite interactive-shell event monitor or audit wait under the runtime contract, alongside native child notifications. It wakes the existing authorized task; it is not another goal or executor. Inspect exact run status and settled artifacts, never treat silence as success. At each tick, re-read this packaged Pi-adapted playbook by its resolved local path, not from the target project's trunk, then inspect the current goal through its public status/get surface. Audit the operation against both. Fix drift during that tick and treat it as urgent. Probe each owner with a generic liveness or status check, and collect the decision trails. Check every task-local child receipt against exact native status and output, including after the final merge. A read-only lane can legitimately produce no side effects; silence alone never proves a stall. A lane error blocks its work. For an overdue lane, inspect evidence against its expected runtime before diagnosing a stall. Request a safe checkpoint and interrupt/stop the exact owned run. Confirm settlement and preserve its partial diff before a same-protocol replacement; unknown ownership blocks a second writer. Never drop a stalled lane's work. End the program only when every delegated run is settled. When merges batch, run a retro pass and a post-merge bot-comment sweep.
7. **Stand down instantly on the operator's stop.** Follow Pause safely: send zero-new-writes guidance to exact owned workers, reconcile interruption/stop and artifacts, stop owned monitors, and request the user's goal pause. A receipt does not prove the worker has stopped. Unrelated workers/goals stay untouched.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
