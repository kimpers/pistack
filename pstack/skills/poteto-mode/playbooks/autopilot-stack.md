### Autopilot-stack

Read [the Pi integration contract](../../../../pi/references/integration.md) first. Paths in prose are relative to the poteto-mode skill directory unless explicitly linked.

**You own the stack, never the landing. Hand the operator one linear stack of base-chained PRs to review and land.** Autopilot-full holds except for how verified work leaves. Re-read both packaged Pi-adapted playbooks at each authorized tick. This playbook wins where they differ.

Read [runtime](../../../../pi/references/runtime.md) and [delegation](../../../../pi/references/delegation.md). Owners are parent-managed bounded phases, not nested orchestrators. Publication requires explicit authority. No owner merges, arms auto-merge, or closes. Helper-dependent steps need readiness and the relevant qualification. Use approved model selectors and preserve inherited effort, saved panels, and concurrency.

1. **Run Autopilot-full's owners, minus topology and landing.** Owners report code-ready and STACK-READY with exact heads in place of merge-ready. They never rebase onto another branch, trunk included, and never retarget, merge, close a PR, or arm auto-merge. The root owns topology and the operator owns landing. Dependent items branch from their parent's branch, not trunk. Apply Autopilot-full step 4's full-swarm-once and single-verifier rules, with STACK-READY receipts. Nothing enters the stack unverified. Owners retain skeptical Bugbot triage per `references/bugbot-triage.md`.

   Preserve a checkpoint at every verified-unit boundary under explicit publication authority. Expected-red states remain inside that unit. Follow Autopilot-full step 6 for an audit every hour through an explicitly owned finite interactive-shell monitor, never an automatic goal or scheduler. Confirm settlement and preserve partial work before replacement. State-then-wait and the operator's zero-writes hold apply unchanged.
2. **Give topology one writer.** Owners push only their own branches and report the tip, current base, and intended parent. Only the root rebases or retargets a link. Append clean PRs in dependency order, setting each base to its parent's branch with `origin pr edit <pr> --base <parent-branch>` or `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never require `gt`.

   Transfer exclusive write ownership before a root topology operation. Confirm the owner has stopped writes and preserve its work. Fetch the exact intended parent tip and check `ls-remote` before an explicitly authorized push with `--force-with-lease` pinned to the known remote SHA. On a conflict, the owner resolves only its slice under a serialized handoff for the root to push. Afterward the owner takes the root's push as its new base and lease before resuming. An unexpected push blocks reconciliation rather than being overwritten.
3. **Absorb drift at the root.** Until landing starts, apply Autopilot-full step 5's tested-merge-result rules to each link. The root rebases bottom-up only where those rules require it. Apply Shipping's patch-id rule link by link because each link's base is its parent. Re-run mergeability and CI at every new head, even if a verdict survives. Invalidated proof returns through Autopilot-full step 4's appropriate verifier round. Gate loosening still requires proof and the root's fresh countersign within explicit approval authority.
4. **Deliver the chain, then keep hands off it.** Each link carries its verified patch and verdict in the PR through authorized publication. The operator reviews and lands bottom-up. Once landing starts, nobody writes the chain except the post-merge retarget and patch move sanctioned by `playbooks/shipping.md` step 4, performed by the single authorized topology writer. A mid-landing problem goes through the root to the operator. Any fix waits for the operator's go.

**Choosing between the autopilots.** Autopilot-full when PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, work is sequenced or coupled, or merge authority is withheld.

**Reply:** use **ketchup**, with links to the stack root and tip, a one-line verdict per link, and anything parked or excluded with its reason.
