### Shipping

Read [the Pi integration contract](../../../../pi/references/integration.md) first. Paths in prose are relative to the poteto-mode skill directory unless explicitly linked.


**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.** For "land the stack", "ship it", "enable merge when ready", or the second half of a stack that **Babysit** already drove to green.

This is the half after `playbooks/babysit.md`.

Publication and landing require explicit approval. Use one parent-owned topology writer and confirm native settlement before any write transfer. Packaged children return evidence, not merge authority. Keep exact approved model selectors, saved panels, inherited effort, and concurrency through [delegation](../../../../pi/references/delegation.md).

1. **Resolve the forge, then verify every PR independently.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr ...` for PR view, watch, edit, and merge operations; otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One independent local verifier per PR, within configured concurrency, exercising the real surface via the verification contract against base versus head. Require a discovered profile with actual control tools, or block live proof. Each returns `PASS`, `PASS+NOTES` or `FAIL` with evidence. The parent posts only when authorized; missing external-post permission does not justify a fabricated posted verdict. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first without `PASS` or `PASS+NOTES`. Report that ceiling. A verified PR above a gap waits because it cannot land without the code below it. A branch that neither holds nor needs that code may move onto trunk under explicit topology authority and land independently, but needs a fresh verdict on that new base.
3. **Re-check that each verdict still describes the patch.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that PR's base-to-head diff. A rebase or base retarget rewrites SHAs and can silently invalidate a verdict without touching a check. Before landing a PR, compare the recorded patch-id with its current base-to-head patch-id. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, that lane's result stays valid, and checks and a review of the change run fresh. Do not reuse a lane result from a dev server or from anything else with no build output. Rerun that lane. Re-verify anything else when the patch changed. When it did not, keep the code verdict but re-run mergeability and CI at the current head. Never use matching commit messages or a green check from an older SHA as a substitute.
4. **Land bottom-up, one PR at a time.** Before landing starts, prepare only the lowest verified PR on fresh trunk and re-run step 3. Never merge a child into its parent's branch. Confirm the current bottom PR targets trunk and its exact head has green checks and a valid verdict. Merge only that PR with `origin pr merge <pr>` or `gh pr merge <pr> --squash`. Origin's plain command also merges every PR below the named PR, so never name a descendant instead of the bottom. Arm `--auto` only for the current bottom when the user explicitly requested merge-when-ready and its verdict covers the current head.

   Read the PR back with `origin pr view <pr>` or `gh pr view <pr> --json state,mergedAt,baseRefName`. A merge command can report success when a merge queue only queued the PR. Auto-merge requested is not merged. A landed PR reads merged with trunk as its base, not its parent's branch. Confirm the merge result on trunk before advancing.

   After a confirmed merge, the single authorized topology writer performs the post-merge move. Retarget only the PR whose base was the merged branch to trunk with `origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`. Move that child's patch onto the merge result. Publish only with an `ls-remote` check and `--force-with-lease` pinned to the known remote SHA. An unexpected push blocks the operation. Apply step 3's patch-id and per-lane rules to decide whether the verdict survives. Re-run mergeability and CI at its new head before merging it. Do not retarget, arm, or merge higher descendants yet.
5. **Leave the stack alone while it lands.** Step 4's post-merge move is the only permitted branch or base change. No second writer or opportunistic fix enters a landing in flight. An unexpected problem goes to the operator before mutation. A base moving to trunk after its parent merges is expected, not damage to repair.

   On GitHub, watch the frozen bottom-to-top verified run with `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>` under the owned Pi event monitor in [runtime](../../../../pi/references/runtime.md), after approved helper setup and installed CLI and forge qualification. Re-read the active PR after each wake. `READY` or queued `WAITING` with reason `merge-queue` is not a merge. Shipping waits for actual merged state and ultimately `COMPLETE` at the ceiling, rather than Babysit's merge-ready stop. Silence, timeout, or a requested auto-merge proves neither. Keep queued completion tied to actual merges. Closed-unmerged, failed or cancelled required checks, and dirty or unstable merge state require diagnosis rather than advancing the run. Pending or blocked checks alone are not proof of failure or completion.

   On Origin, use `origin pr checks <pr> --watch` and re-read `origin pr view <pr> --checks` until the ceiling reads merged. The retained GitHub watcher and frontier helper do not prove Origin state. Never combine Origin topology with gh evidence. GitHub `autoMergeRequest` says only that auto-merge was requested for one GitHub PR, not that a stack or Origin merge-when-ready is safe. Missing active-forge evidence stays unknown. Diagnose a stall before changing anything.
6. **Stop at the ceiling.** Report what actually landed, how it was confirmed, and the next unverified gap. Extending the run requires new verdicts and a new pass through step 1.

**Reply:** the verified run and ceiling, each verdict and its verifier, what landed and how it was confirmed, any armed but unmerged PR, and what the next gap needs.
